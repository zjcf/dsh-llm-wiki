# LLM Wiki

LLM Wiki 是面向 DeepSeek Harness（DSH）的知识库插件，npm 包名为 `dsh-llm-wiki`。通过管理页或对话收录材料、整理和维护知识，并提供本地查询、原件预览、Git 版本历史及自动同步。

## 安装与使用

`dsh-llm-wiki` 在 DSH Web 侧栏提供「知识库」，使用 DSH Host 的 Node.js（22.13.0 及以上）和 npm 依赖。索引使用 [Node 内置 SQLite](https://nodejs.org/api/sqlite.html)，不需要另装数据库服务、Python、本机 Git、`pdftotext` 或项目源码。

插件不绑定组织 scope 或私有 registry，使用安装端配置的 npm 源。包发布到所选源后，可通过包名安装：

```bash
dsh plugin --profile web add dsh-llm-wiki@0.12.4 --save-exact
```

也可在 DSH「添加插件」中填写包名 `dsh-llm-wiki`，选择实际发布该包的安装源。尚未发布时，可在源码目录执行 `npm pack` 构建 tarball，再通过本地 tarball 安装。

包名、客户端模块和 bundle patch 统一使用 `dsh-llm-wiki`，管理 API 路径为 `/api/dsh-llm-wiki`，上传路径为 `/api/dsh-llm-wiki-upload`。从旧的组织 scope 包迁移时，先停用旧插件，再安装新包，并将 `root` 指向原知识库目录；保留原插件配置及宿主凭据，避免同时启用两个实例管理同一目录。插件仅迁移原样生成的旧工作区指引，保留用户自定义内容；已有 Git 同步凭据引用继续可用。安装后刷新 Web 客户端以加载新的侧栏入口。

插件启用后，从侧栏打开「知识库」。在「来源材料」导入文件，点一行直接预览原件：PDF 使用浏览器 PDF 阅读器，Word（DOCX）使用随包提供的本地浏览器渲染器，显示图片、表格、页眉页脚和分页。Word 字体与分页可能与 Office 略有差异；旧 `.doc` 需先转为 DOCX。预览不向外部服务上传文件。Word 在独立沙箱内运行，不允许外部网络请求或访问 DSH 页面。单文件上传上限 25 MiB。

0.8.0 起，插件自带 `/llm-wiki` 查询技能，在任意工作区的当前会话输入 `/llm-wiki 你的问题` 即可主动调用；DSH 的技能目录也向 Agent 提供它，遇到本地资料查询时可自动选用。技能先用 `wiki_search` 检索已整理知识，再用 `wiki_read_page` 实际读取命中内容并附来源；必要时核对原文。有足够依据即停止，不全库扫读。默认只查本地库，未命中时说明当前库的证据缺口；只有用户明确要求外部补充或核对最新信息时才联网，并区分库内与外部来源。技能不改变当前/默认工作区，不在普通查询时导入、改写或删除知识。它通过 DSH 原生技能注册随插件启停，无需复制到项目或用户技能目录；关闭自动整理不会关闭查询技能。斜杠候选未更新时刷新 DSH 页面。

查询回答直接给出所问答案并附知识页链接，简单问题通常一两句话；不因 `basis: conversation` 或缺少附件追加免责声明，也不固定列出“结论/依据/限制”、无关关键词检索记录或额外排查建议。只有内容明确待核实、过期、存在冲突，或不足以回答所问时，才说明影响本次答案的具体问题。这条规则同步提供在 `/llm-wiki` 技能、知识读取返回及插件生成的工作区指引中；不会自动改写已有知识正文；旧正文中与本次问题无关的缺项说明也不默认复述。

通过对话录入或更正知识时，Agent 先检查含义、矛盾和影响复用的缺失信息，按需集中追问，等用户补充后再保存；已有信息不重复问，信息完整时直接保存。BUG/修复记录重点确认产品及模块、现象和触发条件、影响版本或环境、修复版本，以及能否不升级临时处理；有临时方案时补充步骤、适用条件和必要风险。未知、未确认、无临时方案分别按用户说明记录，不推断；用户明确要求先保存已有信息时允许保留具体缺项。其他知识按类型澄清，不强制填写 BUG 字段。该流程由 `/llm-wiki` 技能、知识写入工具描述和工作区指引共同提供，不新增后端必填字段；普通查询和已导入文件的自动整理不套用录入问卷。

PDF/DOCX 内嵌图片提取到 `extracted/assets/<source_id>/`。提供给 Agent 的 Word 正文保留标题层级、列表、表格行列和图片段落位置；PDF 根据文字和位图坐标恢复图文顺序，多栏和复杂版式仍需核对预览。Agent 将相关图片嵌入所解释的章节或步骤，保存工具不会追加末尾图库。0.4.0 生成的受标记图库在展示和检索时忽略，磁盘中的旧知识正文不自动重写。

0.5.0 启用时会更新旧 PDF/DOCX 的机器抽取结果，保留原件、已有知识及人工阅读版的证据锚点。DOCX 抽取支持内嵌 PNG/JPEG/GIF/WebP；外链图片不下载，EMF/WMF 等不支持的格式会记录限制。PDF 不还原矢量绘图和完整页面版式，不自动 OCR。每份材料最多抽取 200 张、总计 64 MiB，单张 PDF 图片最多 1600 万像素；Word 预览解压上限 72 MiB。提取成功不代表已经理解图像，视觉核对通过 DSH 当前模型完成。

默认数据目录是 DSH Host 的 `$DSH_HOME/llm-wiki`（未设置时为 `~/.dsh/llm-wiki`），首次启动自动创建并登记为 DSH 的「知识库」工作区。也可以将插件组件 `llm-wiki` 的 `root` 指向 Host 上已有 DSH 工作区的绝对路径。若已有知识库需要迁移，先复制库目录并核对数据，再切换配置。已运行的 Web 客户端如未显示侧栏入口，刷新页面。安装包升级或卸载与库目录分开。

通过 Web 新导入的材料，抽取到正文后，自动交给 DSH 当前默认模型整理。先生成来源页作为追溯入口，再判断是否值得创建或合并主题、实体、QA：主题用于概念、规则和流程，实体用于材料实际描述的对象，QA 用于能直接复用的问答或操作方法。不是每份材料都生成三种知识；短操作流程可保留步骤沉淀一个 QA，不把每个名词或命令拆成实体。新增或更新的知识必须引用本次来源，优先检索并合并已有页，不能自动删除其他材料或知识。

整理长度与材料匹配：简单 Markdown 保留实际要点或步骤，不套审计报告模板、不补写背景和原文未提到的缺失项；`reviewGuide` 提供来源摘要长度上限。重复上传沿用原记录，升级不自动重写旧知识；「重新整理」可按新规则排队。来源摘要、独立知识处理完成后才结束任务。抽取有缺口时最多标为「部分整理」，失败可重试。`autoReview: false` 可关闭自动整理。

0.6.0 起，自动整理使用 DSH 普通会话接口创建并绑定「知识库」工作区，对话标题为「整理 · 文件名」。运行中可以从侧栏或来源详情的「查看整理对话」查看过程；完成、失败后均保留，不自动归档。重试创建新对话，来源详情指向最近一次，旧对话仍保留在工作区。插件停用会取消正在执行的整理，但不删除处理记录。

0.8.1 面向 DSH 0.2.2-rc.1：整理 preset 显式挂载宿主原生工具执行器，不再调用已移除的 `tools.presentAs()`，不支持旧版工具呈现接口。启动或执行异常会显示失败阶段，避免一律提示检查默认模型；未配置默认模型时仍明确提示配置。

插件提供的是 **DSH 原生 Agent 工具**，安装后直接可用，无需额外配置 MCP 服务；它没有独立的通用 MCP 服务入口。0.12.0 恢复普通 Agent 的完整知识维护能力：

- `wiki_import_source`：收录当前对话附件（`file`）或用户文字（`content`），保留原始字节、按内容去重。自动整理启用时排队；关闭时保留待整理来源。
- `wiki_reorganize_source`：复用原件重新整理，运行中的同一来源不重复派发。
- `wiki_write_page`：新增或整体更新主题、实体、QA，维护引用、索引、日志及 Git 提交。更新须提供 `wiki_read_page` 返回的 `expected_revision`。可关联实际 `source_ids`；管理员通过对话录入的知识可不创建来源文件，标记 `basis: conversation` 以追溯录入方式，与文件整理的知识均可用于回答。保留用户给出的范围和不确定性，不补写未提供的事实。
- `wiki_update_page`：基于 revision 精确替换一段正文，保留其余内容与来源。
- `wiki_delete_source`、`wiki_delete_page`：先只传 ID 查看影响，再携带返回的 token 执行；并发变化后拒绝旧 token。来源删除会删除原件和关联知识，多来源页按剩余来源重整；独立知识页删除保留原件。Git 历史保留，版本回滚仍只通过管理页 revert。

查询工具为 `wiki_list`、`wiki_search`、`wiki_read_page`、`wiki_get_source`、`wiki_read_source`、`wiki_read_image`，以及结构体检工具 `wiki_lint`（在索引 Worker 中基于引用图列出孤立知识页、目录未收录页、失效链接和未完成整理的来源，每类返回总数和前 `limit` 条，只读）。内部来源登记 `wiki_record_review` 不向普通对话开放；自动整理仍在独立会话中按完整阅读范围生成一个整理提交。

插件配置 `readOnly: true` 时，仅注册上述七个查询工具，拒绝所有管理 POST、删除预览和版本写入，不执行迁移、补抽取、自动整理、恢复任务或 Git 推送。管理页标明只读并隐藏写入按钮。`cacheDir` 指向共享知识库以外的绝对路径，默认 `$DSH_HOME/llm-wiki-cache`；每个实例各自维护派生索引，可读取管理实例发布的新提交。知识库卷须同时以 Docker `read_only: true` 挂载，约束宿主 Shell/文件工具。详见 [双实例部署](deploy/README.md)。

管理实例仍使用原有导入、删除与版本管理页。插件只迁移自己原样生成的旧工作区指引，保留用户自定义 `AGENTS.md`；所有变更应走工具，不直接改写原件、manifest 和索引。

查询使用 `wiki_search`，默认最多 5 条并按来源去重，机器抽取文本与阅读版不会重复占位。索引保留原文标题，AI 改写知识页标题后仍能命中；结果提供原文标题 `sourceHeading`、稳定 `sourceId` 和可直接调用的 `readTool`/`readArgs`。`wiki_read_page` 同时接受已登记的知识页、抽取文件或来源 ID，可按 `query` 定位知识页章节，默认 60 行、最多 8000 字，有足够依据即可停止，不全库扫读。工具返回 `nextLine`/`nextColumn` 供续读；自动整理未完整读完时不能标为 processed。命令行提供 `dsh-llm-wiki --root <库目录> status|import|extract <source_id>|search|check`。管理、预览、图片和原件接口均沿用 DSH 登录鉴权。

0.8.0 同时修复旧来源/知识页缺少可选元数据时的工具返回：省略未定义字段、无原文标题时回退文件名，避免 DSH 拒绝非无损 JSON，导致搜索命中后无法读取正文。

插件后端入口是 `src/extract.ts` / `src/docx.ts`（结构与图片抽取）、`src/wiki.ts`（归档与登记）、`src/dsh.ts`（Agent 工具）和 `src/cli.ts`（npm 命令）。Word 预览由 `docx-preview` 在本地浏览器完成。自动整理使用专用 Agent preset，只开放 Wiki 读取、检索、来源登记和有本次来源依据的知识写入，不开放 Shell、子 Agent、导入和删除。完成后移除本次任务的写入工具并释放临时限制，可继续查询和对话。

清理过期资料时，在「来源材料」点「删除」，核对影响清单后确认。插件会从当前库删除原件、专属来源页、抽取文本与关联阅读版，并关联删除依赖该来源的主题、实体和问答，同步清理目录及失效引用。关联关系同时检查 `source_ids`、原件/来源页链接与跨知识页引用，兼容旧页面。

只依赖该来源的知识直接删除，不保留「待复核」正文。多来源知识先移除旧页，再为每个受影响知识页创建一个持久化任务，由 DSH 默认模型完整读取剩余来源后重新整理；不把旧正文或被删除来源交给重整任务。正文、依据、目录与完成状态检查通过后在同一事务内重新发布。剩余证据不足时可以保持删除，并记录原因；失败时旧页不参与查询，管理页提供重试与查看重整对话。连续删除会合并任务并排除已删除来源；服务重启中断的任务标为失败，不静默重复运行。自动整理关闭且存在多来源知识时，需先启用再删除。

删除与重整仍自动保存版本并推送；历史版本保留原件和知识副本，可通过管理页 revert 恢复，禁止 force push。直接删除某个独立知识页的行为仍是保留原件并清理引用。此功能不表示从历史和远端彻底清除内容。

### 大数据量与按需加载（0.11.0）

来源、知识页、关联知识和版本历史均在服务端分页，管理页每页最多 50 条；重整任务每页 20 条。翻页替换当前页，不在浏览器持续累积列表。来源列表只返回元数据；原文、知识正文及关联页按打开的对象单独读取，跳转到本页列表之外的来源和知识也能正常打开。

全文检索、元数据索引及关联引用图在独立 Node Worker 中建立和查询，不占用 DSH 主线程扫描正文。派生缓存为 `.wiki/catalog.sqlite*`，不包含在 Git 数据版本或远端同步中；删除缓存后可从库文件重建，损坏缓存会隔离后重建。首次来源列表不等待全文索引；首次打开知识列表或搜索时建立正文索引并显示进度。后续按提交更新，仅重新读取变化文件。短关键词保持词面匹配，不引入语义向量或外部搜索服务。

版本列表用游标翻页；差异先按每页 50 个文件加载路径，展开某个文件才读取和计算其差异。原件不加载到差异正文；过大的文本只显示变更记录，避免大量二进制或长文直接进入浏览器。状态轮询读取最近的巡检结果，不重复哈希全库；后台约每分钟巡检一次，也可在版本页手动刷新。业务写入和同步前仍检查未登记改动，未变化文件复用由 inode、大小、纳秒修改时间与状态变化时间校验的 Git 对象。

可执行 `rtk proxy node scripts/benchmark-catalog.mjs 10000 /tmp/wiki-scale.json` 复现隔离压测（先构建）。脚本生成 1 万份来源、1 万个知识页及 5001 个历史版本，测量冷索引、分页、搜索、主线程延迟和历史状态；完成后自动清理临时库，不向现有知识库或远端写入测试数据。耗时会随正文量和磁盘变化。

### 版本历史与自动同步（0.9.0 起，0.11.0 合并整理提交）

首次启用为当前数据建立初始版本，无法补录启用前的历史。导入原件单独保存一个版本；一次自动整理或删除后重整完成后只保存一个提交并自动推送，来源页、知识页、目录和日志一并保存。整理过程中的工具调用保留在 DSH 对话里，草稿不进入当前库或 Git；失败、超时或服务中断不会发布半成品。与其他写入发生版本冲突时停止整批覆盖，重试时重新读取当前知识。重复导入和未改变持久内容的运行状态不会重复提交。

已有版本和历史分组保持原样，不 squash、不 amend、不 force push。新整理通过一个 revert 提交撤销对应的单次提交，旧整理仍支持按会话撤销整组历史。

数据版本使用纯 JavaScript Git 库，保存在库内独立的 `.wiki/history.git/`，不接管工作区已有 `.git`。版本覆盖 `raw/`、`extracted/`（含图片）、`wiki/`、`.wiki/manifest.json`、`index.md`、`log.md`、`README.md` 和 `AGENTS.md`；不包含同步配置、Token、锁、临时文件和插件源码。原件与图片会占用历史存储；历史不会自动过期或裁剪。已删除的文件仍可在历史与已同步远端中恢复。

「版本历史」提供提交记录、整理分组、差异、外部改动检查、同步状态和 revert。选择普通提交可反向应用该提交；选择「整理完成」可撤销本次会话的全部提交，保留期间穿插的其他来源导入。撤销先检查关联文件和冲突，确认后生成新的 `Revert` 提交，不 reset、不 amend、不倒退分支。引用或登记检查失败会恢复操作前状态。存在运行中的整理时不能撤销；历史中的运行标记不用于重新派发任务。

在「同步设置」填写 HTTP(S) 仓库地址、分支和 Token。建议使用 HTTPS；用户明确配置内网 HTTP 时，页面会提示 Token 经网络明文传输。GitLab 用户名由插件填写；Token 须有目标仓库和分支的推送权限，保存到 DSH 凭据服务，普通同步配置只保存引用。Token 留空保留；更换仓库或分支必须重新填写。禁止把凭据放入 URL，遇到 HTTP 跳转会拒绝请求，避免跨地址发送凭据。仓库地址留空可关闭远端同步，本地历史继续保留。

本地 commit 后自动后台 push；网络失败保留待同步版本并重试，也可点「立即同步」。启动时补推，DSH App 关闭期间不运行定时任务。远端需为空仓库或包含本库当前历史；若已有独立历史、权限不足或分支分叉，停止同步并提示，不自动合并或覆盖。插件唯一的 push 入口固定 `force: false`。要限制其他客户端强推，还应在 GitLab 保护目标分支并关闭 force push；插件的仓库写 Token 不承担管理远端分支规则的职责。

0.9.1 在同步错误中显示 Git/HTTP/网络错误码，帮助区分配置已保存与远端推送失败；不返回服务端原始错误或认证值。

启动时和每天（北京时间）检查未登记改动，未记录的文件变化不会被后台自动接受。发现后暂停业务写入与同步，管理页展示差异；核对后可以登记为「未核实的外部改动」，再通过 revert 撤销。写入中途失败和未提交事务会恢复前一版本；同步异常不回滚已保存的本地版本。

Git 负责记录、检测与恢复，不判断知识是否正确。数据目录和本机历史由同一系统账户控制时，该账户仍可修改两者；需要抵御此类攻击时，应增加独立写入账户、受保护的异机远端或独立备份。Git author 使用插件服务标识；来源 ID 和 DSH 会话用于追溯，不冒充真实用户身份。

## 日常使用

- 收录文件：在 DSH 知识库管理页导入，或把文件附在 DSH 对话中要求收录；插件保存原件并在启用自动整理时创建整理对话。
- 录入知识：通过对话提供描述或 QA，Agent 先澄清必要信息，再保存知识页，可不创建来源文件。
- 查询：在当前会话输入 `/llm-wiki 你的问题`，优先检索本地知识并引用知识页。
- 查看原文：在「来源材料」列表点击文件预览 PDF/Word，在知识页追溯相关来源。
- 维护：通过管理页或管理实例的 Agent 工具修改、重整和删除；只读实例只提供查询。版本回滚使用管理页 revert。
- 体检：输入 `/llm-wiki 体检知识库`，Agent 先用 `wiki_lint` 获取孤立知识页（没有其他页面链接）、目录缺项、失效链接和未完成整理的来源，再读取相关页检查矛盾、过时结论、缺少独立页的概念和缺失的交叉链接，列出问题与建议，确认后才修改；只读实例也可体检。管理页「检查知识库」另外校验原件哈希与登记一致性，并列出孤立知识页。

### 目录、交叉链接与日志

`index.md` 按「来源与原文」「主题知识」「实体知识」「QA 问答」分节，每条为 `- [标题](路径) — 一句话摘要`；摘要来自 `wiki_record_review` / `wiki_write_page` 的可选 `summary`，局部修改时保留原摘要。升级后首次启动会把旧版平铺条目（`· 主题知识` 等后缀）迁移到对应分节，记为一个维护提交，手写内容保留。

知识页正文可用 `[标题](wiki/topics/xxx.md)` 按知识页 ID 链接其他页面，保存时转换为相对路径；新增的链接指向不存在的页面会被拒绝。自动整理会链接确实相关的已有页，并在新材料与已有结论矛盾时写明差异及各自来源，不静默覆盖。查询综合了多个知识页并形成可复用结论时，Agent 会询问是否保存为 QA，经同意才写入。

`log.md` 新条目统一为 `## [ISO 时间] 操作 | 对象`，操作包括 `ingest`、`page`、`delete`、`rebuild`、`extract`、`revert`，可用 `grep '^## \[' log.md` 按日期或操作过滤；旧条目不改写。

## 开发与验证

本仓库保存插件代码、测试、构建脚本和部署说明。知识库运行数据由插件在 DSH Host 的配置目录中创建，不随源码或 npm 包分发。不要在源码仓库根目录运行面向数据目录的初始化、导入或版本操作。

```bash
rtk proxy npm ci
rtk proxy npm test
rtk proxy npm run build
rtk proxy npm pack
```

`npm test` 构建服务端及 Web 客户端，并使用临时目录验证文件抽取、Agent 工具、只读权限、分页索引、整理事务、版本回滚及 Git 同步。发布检查实际 tarball 中的服务端、客户端、CLI 和 bundle patch，凭据与业务数据不得进入发布产物。

源码结构：

```text
src/                  TypeScript 服务端、DSH 工具、技能及 Web 管理页
scripts/              客户端构建与隔离压测脚本
tests/                自动化测试与升级指引样本
deploy/               Docker Compose 双实例部署及运行说明
dsh.patch.yml         DSH bundle 组件定义
AGENTS.md             插件开发与维护约定
```

知识库运行目录结构（由插件维护）：

```text
raw/                  来源原件，按内容哈希归档
extracted/            可检索正文、阅读版与图片
wiki/sources/         来源摘要与原文入口
wiki/topics/          主题知识
wiki/entities/        实体知识
wiki/answers/         可复用问答
index.md              知识目录
log.md                维护记录
AGENTS.md             DSH 工作区指引
.wiki/manifest.json   来源与整理状态
.wiki/history.git/    版本历史
```

原件可以归档任意普通文件；文本、HTML、PDF 和 DOCX 由 Node.js 后端抽取。扫描件不自动 OCR，抽取缺口会记录为限制，不将抽取成功视为已经完整阅读。每份来源的 `extraction` 表示抽取能力，`status` 表示整理进度：`pending`、`partial` 或 `processed`。同一内容去重；同名不同内容分别归档；新版本重新导入，不覆盖旧原件。

全部知识页使用普通 Markdown 和相对链接，通过 DSH 管理页浏览和检索。查询默认采用词面匹配；复杂版式、图片和表格需结合预览核对。
